# UX audit — 20 October 2026

A hostile-user walkthrough of the deployed application, in a real browser, at two
widths, in both languages, against seeded data. Everything below was measured or
screenshotted, not inferred from the code.

The crawlers are `scripts/ux-audit.mjs` (every screen, every role, desktop and phone)
and `scripts/real-user-check.mjs` (the sign-up path end to end). Both drive Brave
(`/usr/bin/brave-origin`) rather than the bundled Chromium.

---

## How this was done

Three accounts, seeded with a catalogue, five batches, stock, a requisition, a
vehicle, a trip and two alerts — because a UI review against empty states finds
nothing. Every route was visited as every role that can reach it, at 1440×900 and
390×844, in English and Arabic. Each visit recorded: time to first byte, total
time, request count, console errors, failed requests, how much text was on the
page, how many interactive elements it had, how many table rows, and a full-page
screenshot.

Load performance is **not** a problem. Time to first byte ranged from 167ms to
950ms, and every page is server-rendered, so the data is in the HTML rather than
fetched afterwards. The Browser job's comment about cold compiles on a preview
describes the preview, not the product. Everything below is about what is *on* the
page, not how fast it arrives.

## P0 — broken, and visible

### 1. The Inventory hub reports zero stock when there is stock

> "**0 combinations in stock across every location**" — with 650 units on hand,
> 5 batches and 5 positive balances in the database.

`stock_balances` has no `id` column. Its key is `(tenant_id, location_id,
product_id, batch_id)`. The hub counts it with:

```js
supabase.from('stock_balances').select('id', { count: 'exact', head: true }).gt('qty_on_hand', 0)
```

PostgREST answers `42703: column stock_balances.id does not exist`, the count comes
back zero, and the page confidently tells a distributor they have nothing. The
dashboard on the same screen says 650 units. Two numbers, one screen, one of them
a lie — and it is the one on the page you visit to answer "do I have stock?".

`apps/web/src/app/[locale]/admin/inventory/page.tsx:38`

### 2. A translation key is the column header

The stocktake sheet's first column header renders the literal string
**`inventory.batch`**. Not a missing translation that falls back to English — the
raw key, as a table header, in the middle of a working screen.

### 3. A translation key is the warning text

Under the first batch on the same sheet, in warning orange, the literal string
**`stocktake.expiringSoon`**. A shelf counter reading it learns nothing about
what the batch is about to do.

Both of these reach production because a missing translation key does not fail a
build. `next-intl` logs it, renders the key, and the page carries on. There were
**six** such keys in the tree; `scripts/check-i18n-keys.mjs` now finds them, and it
is wired into CI.

### 4. The sign-in form puts the password in the URL

Click "Sign in" before React has hydrated and the browser submits the form
natively, as a **GET**:

```
/en/login?email=audit-admin%40gmail.com&password=Audit%23Probe2026x
```

The password is now in the address bar, in the browser history, in the Referer
header of anything the page loads next, and in any proxy or server log along the
way. It happens on a slow connection, on a cold cache, or when the device is
under load — exactly when a person is least likely to notice.

The crawlers fell into it on the first run, which is how it was found.

### 5. The navigation always wraps, and its second row escapes the header

Measured across six viewport widths:

| viewport | header height | nav width | nav rows |
|---|---|---|---|
| 1024 | 65 | 471 | **2** |
| 1280 | 65 | 727 | **2** |
| 1440 | 65 | 742 | **2** |
| 1920 | 65 | 742 | **2** |

The header is capped at `max-w-7xl` (1280px), so the navigation never gets more
than 742px — and the ten destinations need about 890px. It wraps at *every*
desktop width, including 1920px. The header row is `h-16` (64px, fixed), so the
second row of items does not fit inside it: "Analytics" and "Audit log" render
**below the header's glass panel, on the page background**, visually detached
from the navigation they belong to.

It is on every authenticated page, in both languages, and it is the first thing a
person sees.

The code and its own comment disagree about this. `app-nav.tsx` says the
navigation "is hidden rather than shown wrong" below `xl`; the class is
`lg:flex-wrap lg:overflow-visible`, so it wraps instead.

## P1 — wrong, or actively misleading

### 6. The dashboard reports a loss that did not happen

> **Margin if stock is sold: −EGP 62K** — on a red, notched card.
> *"No sell prices entered yet"*, in the hint beneath it.

With no sell prices, retail is zero, so margin is minus the entire cost of stock.
The card is styled `bad`, reads as a 62,000 EGP loss, and contradicts the sentence
underneath it. The honest value is "not available yet" — there is no margin to
report.

### 7. Every stocktake line asks for a reason for a variance it does not have

The "Reason for a variance" select is on every row, always, with a default of
"—" — before a single number has been counted. Half the reasons will be noise in
the audit trail, which is the one record that is supposed to mean something.

### 8. The count input is a 60px box with no label

The "Counted" column header is right-aligned; the input under it is left-aligned
and 60px wide. A shelf counter has to infer that the small empty box is where the
number goes, and that the dash in the "Variance" column is the difference.

## P2 — design and efficiency

These do not break anything. They are the reasons the app feels slower and more
cumbersome than it is.

9. **The catalogue has 89 interactive elements for 5 products.** "Edit" and
   "Deactivate" on every row give a destructive action the same weight as a
   routine one, and nothing on the page says how much of each product is held.
   For a distributor, quantity-on-hand is the column people came for.

10. **"Add a product" and "Add a storage location" are full-width bordered
    strips**, one word each, stacked — two entire rows of chrome for two actions.

11. **The alert centre shows "Scan complete."** nobody asked for. A status line
    for an action that was not taken.

12. **Severity is a bare dot.** CRITICAL and INFO are the same 6px circle in
    different colours, with no legend, on a screen whose whole job is triage.

13. **A 300px-tall teal panel contains "EGP 0".** The empty state is centred in
    a block the size of a small screen.

14. **"TOP PRODUCTS BY DELIVERED MARGIN"** has an empty state that says nothing
    about products.

15. **"EGP 62K"** is too terse for a finance screen. "EGP 62,400" reads better
    and costs nothing.

16. **On a phone, four of ten destinations are visible**, with the scrollbar
    hidden and no fade — the strip used to have one, and it was removed because it
    hid the last three destinations. Since the strip now genuinely scrolls at
    every width, a short fade is safe where the old 24px mask was not.

## What was fixed, and what was not

**Fixed in this pass**, and measured against the deployed application afterwards:

| # | Fix | Before | After |
|---|---|---|---|
| 1 | Count a column that exists on `stock_balances` | `0 combinations` | `2 combinations` |
| 2 | `inventory.batch` exists, in both languages | `inventory.batch` | `Batch` |
| 3 | `stocktake.expiringSoon` exists, in both languages | `stocktake.expiringSoon` | `Expiring soon` |
| — | `scripts/check-i18n-keys.mjs` in CI | silent | a red build |
| 4 | The sign-in form posts; the password never reaches a URL | in the URL | `method="post"`, no action |
| 5 | The navigation scrolls in one row at every width | 2 rows at 390–1920 | 1 row at 390–1920, never escaping the header |
| 6 | No sell prices means no margin figure | `-EGP 62K`, red | `—`, neutral |
| 7 | The variance reason appears only once there is a variance | on every row | only with a variance |
| 8 | The count input gets a placeholder | an unlabelled box | `Count` |

The navigation, measured after the fix: one row at 390, 768, 1024, 1280, 1440 and
1920, and at no width does anything escape the header.

The repository's own suite, against the deployed application, after the sign-in fix:

  ci-audit-pharmacy@pharmaflow.test lands on /pharmacy and stays there

### Two more bugs the sign-in fix turned up

Fixing the URL leak was not a one-line change, and the two attempts that failed are
worth recording, because both failed in ways that looked like something else.

**An `action` attribute broke every sign-in.** React 19 treats a form with a string
`action` as a form action and submits it natively -- and it does so *after* the submit
handler has run. The password grant succeeded, and then the native POST navigated the
browser to the action and cancelled the client-side navigation that was about to land on
the dashboard. Every sign-in ended at `/login` with a valid session and no error
anywhere. The route it pointed at was removed rather than left as dead code.

**The form sent no email at all.** The two fields were controlled, with their values in
React state. A controlled input is empty until React has hydrated: type into it first and
the keystrokes go into the DOM, React's state never sees them, and the submit sends
nothing. GoTrue's answer was literally `{"code":"validation_failed","message":"missing
email or phone"}`. It is worse than a failed sign-in, because hydration then re-renders
the field and *erases what was typed*.

The fields are now uncontrolled, and the submit handler reads them from the form itself.
What the person typed is what gets sent, whenever they typed it.

**Left for a later pass** — 9 to 16. They are all in the catalogue and the
dashboard, none of them is wrong, and rewriting the catalogue's row layout is a
bigger change than belongs in the same commit as a broken count.

## A note on seeding

`auth.users` rows inserted directly into the database **cannot sign in**, even
with a correct bcrypt hash, a confirmed email and an `auth.identities` row
present. GoTrue answers `invalid_credentials`.

The difference is `instance_id`, `created_at` and `raw_user_meta_data`, which the
Admin API sets and a hand-written INSERT leaves null — and correcting them by
hand afterwards breaks GoTrue's email lookup for the *whole project*, so that the
Admin API starts returning `500 Database error checking email` and no user can be
created by any route.

**Use the Admin API.** `scripts/ci-fixture.sh` already does, which is why the
Browser job works.
